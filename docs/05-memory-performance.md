# 内存与性能预算

## 原则

4 GB 游戏资源只占磁盘，不占常驻内存。禁止以下做法：

- 整个 XP3 读入 `ArrayBuffer`、Blob 副本、MEMFS 或 Wasm 堆。
- 用一个 IndexedDB 记录保存 2 GB 以上文件。
- 下载、哈希和写库同时保留多个完整块副本。
- 无上限缓存解压图像、音频、视频帧或 XP3 段。

## 初始预算

以下是 PoC 初值，不是最终保证值：

| 内存区域 | 初始预算 |
| --- | ---: |
| Wasm 初始内存 | 64–128 MiB |
| Wasm 运行目标上限 | 768 MiB，实机后调整 |
| IndexedDB 读取块缓存 | 16 MiB |
| XP3 解压段缓存 | 1–8 MiB |
| 图像/立绘缓存 | 128–256 MiB，低内存模式可降低 |
| 音频缓冲 | 32–64 MiB |
| 视频解码缓冲 | 64–128 MiB |
| JS UI 与下载临时数据 | 64 MiB 内 |

Android 的 4 GB 是整机物理内存，不是 WebView 单进程可用内存。最终目标应尽量将
WebView 进程工作集控制在 1.2 GB 以下，并以“系统不杀进程”为最终标准。

## 线程策略

目标 WebView 不提供共享 Wasm 内存，目标构建不得启用 pthreads。参考分支当前默认
预创建 64 个 pthread Worker，这一配置只用于上游现代浏览器对照，不能进入产品
构建。引擎、Asyncify 文件读取和渲染先在浏览器主线程形成最小闭环；下载、哈希等
不访问 Wasm 内存的任务可以使用普通 Web Worker。视频优先使用浏览器硬件解码，
Wasm FFmpeg 后备方案必须限制自身线程和缓冲。

Asyncify 会保存和恢复 Wasm 调用栈，`ASYNCIFY_STACK_SIZE` 必须由 D1 的最深实际
读取路径测量后固定。栈溢出、重入和同一时间多次 unwind 都要作为显式失败处理，
不能通过无限扩大 Wasm 内存掩盖。

## 性能测量

- 剧情 FPS、1% 低帧和最长卡顿。
- 启动到标题耗时、场景切换耗时、存档/读取耗时。
- IndexedDB 顺序写、顺序读、随机读和跨块读吞吐。
- Wasm 堆大小、JS 堆、GPU 纹理估算和 Android 进程工作集。
- D1 合成文件桥至少 10 分钟、D3 真实引擎 30 分钟、D5 首个游戏 60 分钟内存趋势。

默认画质以稳定优先：限制纹理缓存、减少预读、视频单线程或硬件解码、后台下载时
降低并发。用户可在设置中切换“省内存”和“标准”模式。
